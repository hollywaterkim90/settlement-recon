# 수수료 검증: 명세 합이 "원장 − 수수료"와 맞는지

## 목표
명세 합이 **원장 총액에서 수수료를 뺀 값(기대 순액)**과 다른 주문을 검출한다.
#2 금액 불일치의 수수료-인지 버전. 설계원칙 1(규칙은 데이터로)의 본격 적용 지점.

## 배경
#2 는 "명세 합 = 원장 총액"을 기대한다. 하지만 **실제 정산은 플랫폼이 수수료를 떼고 준다** —
진짜 기대값은 `명세 합 = 원장 총액 − 수수료`. 수수료율은 채널마다 다르므로 **코드가 아니라 데이터**로 둔다.

## 범위
- **`fee_rule` 테이블 신설**(채널 → 정률). Flyway `V5`. 최소로 채널당 한 행부터.
- **기대 순액 = `amount − trunc(amount × rate)`.** 한 규칙으로 고정(원 단위), DB에서 계산.
  - 구현에서 `round` 가 아니라 **버림(`trunc`)** 으로 정했다 — 우리가 '공정한 값'을 정하는 게 아니라
    **플랫폼 계산을 재현**하는 것이라, 방식이 1원만 어긋나면 정상 건이 전부 불일치가 된다.
    `floor` 아닌 `trunc` 인 이유는 음수(환불)에서 갈리기 때문(음수는 범위 밖).
  - ⚠️ 함정: Postgres `round` 와 Java `RoundingMode` 가 미묘하게 다를 수 있다 → **한쪽(DB)으로 통일**.
- **검출**: 명세 합 `<>` 기대 순액. #2 거울 + `fee_rule` 조인, 비교식만 `amount` → `amount − fee`.
  - #2(순수 sum=amount)는 그대로 두고 **별도 메서드**로 공존(수수료 0/규칙 없는 채널엔 #2가 유효).
- `BigDecimal` 비교는 값 기준(`numeric <>`) — scale 함정 회피(#2 방식 유지).
