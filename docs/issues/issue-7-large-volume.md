# 대용량 첫 맛: 검출 쿼리를 대량 데이터로 돌리고 인덱스로 살리기

## 목표
지금까지의 검출 쿼리(#1 누락 · #2 금액불일치 · #3 유령)를 **대량 합성 데이터**로 돌려
실행계획을 눈으로 확인하고, 인덱스로 개선한다. 설계원칙 4(대용량 전제)를 말이 아니라 **증거로**.

## 배경
지금은 소량 테스트라 부하를 안 겪었다. 조인·집계는 이미 DB에서(원칙대로) 하지만
실제 실행계획을 본 적이 없다. `settlement_line` 은 지금 **PK(id)뿐** →
`batch_id` 스코프가 seq scan 일 가능성이 높다.

## 범위
- **합성 데이터 대량 생성**: 원장 수십만 × 명세 수십만 (부분정산·누락·유령·불일치 섞어).
  정답을 우리가 쥐므로 대량이어도 검증이 성립(#1 방식 유지).
- **EXPLAIN (ANALYZE)** 로 검출 쿼리 3종의 실행계획 확인 → seq scan 병목 식별.
- **인덱스 추가**: `settlement_line(batch_id, channel, order_id)`
  — NOT EXISTS(anti-join)·JOIN+GROUP BY 모두를 살린다. Flyway `V3` 로.
- **전/후 비교**: 같은 쿼리를 인덱스 전(seq scan) → 후(index scan)로 EXPLAIN 비교.

## 결과 (상세 기록: [`../large-volume.md`](../large-volume.md))
측정으로 인덱스 **두 개**가 나왔다 — V3 로 끝날 줄 알았으나 병목이 order_ledger 로 이동 → V4 도 추가:
- **V3** `settlement_line(batch_id, channel, order_id)` — 세 쿼리의 명세 풀스캔 제거(버퍼 ~40배↓).
- **V4** `order_ledger(channel, occurred_at)` — #1/#2 원장 풀스캔 제거.
- 실행시간 (전 → +V3 → +V4): #1 **52 → 45 → 3.5 ms** · #2 47 → 55 → **14.6 ms** · #3 19/15/49 ms(무관, 노이즈).
- 인덱스는 **추측이 아니라 EXPLAIN 이 가리켜서** 넣었고, 전 구간 검출 정답 유지(배치 1: 누락 50·불일치 50·유령 50).

## 범위 밖 (파생/YAGNI)
- 배치 페이징·스트리밍 (대량 결과를 나눠 처리) → 별도.
- 쿼리 리라이팅 튜닝, 파티셔닝 → 인덱스로 안 되는 게 확인된 뒤.
- Kafka/스트림 → 로직·스케일 정답 세운 뒤.
